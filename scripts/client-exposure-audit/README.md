# Client exposure audit

This Playwright harness runs the exposure implementation and element-selector
package from this checkout against an arbitrary client page. It does not
initialize Amplitude or send analytics events.

Build the repository first, then run:

```bash
pnpm build
pnpm exec playwright install chromium
pnpm harness:exposure -- --url https://example.com/products
```

Two files are written under `artifacts/client-exposure-audit/`: the full report,
and a `.settings.json` sibling holding just the settings comparison. The full
report answers:

- Which likely interactive elements are missing from the exposure allowlist?
- Does each generated selector uniquely resolve back to its element?
- Does a semantic component produce different selectors as the page scrolls or
  lazy-loads?
- Do generated-looking IDs or changing classes suggest an additional
  element-selector regex?
- Which selectors exposed at initial load, document scroll checkpoints, and
  overflow-container checkpoints?

## Options

```text
--headed                     Show the browser
--storage-state auth.json    Use a saved Playwright login
--viewport 390x844           Audit a device-sized viewport
--config audit-config.json   Override the allowlist or selector settings
--output report.json         Choose the report path
--no-scroll-containers       Skip overflow-container scenarios
--screenshot page.png        Save a full-page screenshot
```

Example configuration:

```json
{
  "exposureDuration": 150,
  "allowlist": [
    "a",
    "button",
    "input",
    "select",
    "textarea",
    "label",
    "[role=\"button\"]",
    "[data-amp-default-track]"
  ],
  "elementSelector": {
    "enabled": true,
    "shadowDomEnabled": true,
    "maxShadowDomDepth": 10
  }
}
```

`allowlist` replaces the harness default. Likewise,
`autogeneratedIdPatterns` and `unstableClassPatterns` are full replacements,
not additions. The report already accounts for this: every recommended list is
the complete list to paste, defaults included.

## Comparing against the SDK defaults

The `settings` block of the report — also written on its own to
`<report>.settings.json` — holds three snapshots in the same shape so they can
be read side by side:

- `sdkDefaults`: what a customer gets when they change nothing.
- `audited`: what this run actually used.
- `recommended`: what the evidence from this page supports.

`changes` lists one entry per setting with the reason behind it. Scalar entries
carry the three values directly; list entries carry `added` / `removed` against
the SDK default plus entry counts, since the full lists are already above.

`enabled`, `shadowDomEnabled`, and `maxShadowDomDepth` are marked
`harnessControlled`. The harness forces them on to have something to audit, so
their `audited` values describe the harness rather than the customer. The
recommendation for shadow piercing is derived from whether selectors on the
page actually crossed a shadow boundary, not from what the harness ran with.

`auditedCustomizations` names the settings where this run departed from stock
SDK defaults, ignoring the harness-controlled fields. When it is empty, the
`sdkDefaults` and `recommended` columns are a clean before-and-after.

`apply` is the paste-ready form: `remoteConfigPayload` under `remoteConfigKey`
for the element-selector settings, and `sdkOptions` for the allowlist and
exposure duration, which are SDK init options rather than remote config.

Nothing here is applied automatically. Read the diff, confirm the evidence in
`allowlistAdditions` and `patternSuggestions`, then change remote config by hand.

## Reading recommendations

“Likely interactive” is intentionally broader than the SDK default. It includes
semantic controls plus common ARIA roles, `onclick`, and focusable elements.
The missing list is evidence for an allowlist change, not an automatic change:
review false positives such as focusable layout containers.

`allowlistAdditions` reduces that list to the smallest set of selectors that
covers it, preferring semantic selectors such as `[role="button" i]` over the
catch-alls `[onclick]` and `[tabindex]:not([tabindex="-1"])`. A catch-all is
only proposed when nothing else reaches an element, and is flagged with
`broad: true` — it will match elements this audit never saw, so check the
examples before adopting it.

Regex suggestions are conservative and require at least two examples with a
shared prefix. Review them against authored IDs before rollout. The current v1
selector does not emit classes; unstable-class suggestions are included for
class-aware consumers and future selector strategies.

The harness never clicks controls, submits forms, or writes analytics. It does
scroll the document and up to ten visible overflow containers, which can trigger
normal lazy-loading behavior on the page.

Reports include page URLs, element text, IDs, and classes. Treat reports from
client pages as customer data: keep them in approved storage and redact them
before sharing outside the investigation.
