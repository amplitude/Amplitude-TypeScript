# AutoCapture × Shadow DOM — POC (SDKW-51)

**Status:** Proof of concept, working end-to-end. Open-mode shadow DOM only; closed mode is
explicitly out of scope.
**Scope:** Browser SDK capture side — Element Clicked, Element Changed, action clicks,
exposure/zoning discovery, Element Path, Element Hierarchy, labeled-event matching, text masking.
**Try it:** `pnpm dev`, then open `http://localhost:5173/autocapture/shadow-dom.html`
(`?shadow=off` shows the legacy behavior for contrast).

---

## 1. The problem

AutoCapture already *hears* clicks inside shadow DOM — its listener sits on `document` with
`capture: true`, and `click` is a `composed` event that crosses shadow boundaries. It fails
anyway, for four distinct reasons (numbered as in the SDKW-51 status note):

1. **Wrong target.** At a shadow boundary the browser *retargets* `event.target` to the shadow
   **host**. The SDK never sees the real clicked element — so allowlist matching either drops the
   click or attributes it to the host (a bare `<div>` with no text).
2. **The ancestor walk dead-ends.** Everything downstream — allowlist matching
   (`getClosestElement`), Element Hierarchy (`getAncestors`) — climbs `parentElement`, which is
   `null` at the top of a shadow tree. Even with the right target, the hierarchy would stop at the
   shadow root and never include the host or the page context around it.
3. **Selectors can't cross the boundary.** Element Path is a CSS selector, and CSS selectors
   cannot pierce shadow roots: `document.querySelector` will never resolve an element inside one.
   A selector generated *inside* a shadow tree is silently scoped to that tree and won't
   round-trip.
4. **Discovery is blind.** `querySelectorAll` and the `document.body` MutationObserver (used by
   exposure/zoning and viewport-content-updated) don't see into shadow trees. And `change` — unlike
   `click` — is **not** a composed event: it never leaves its shadow tree at all, so the document
   listener never fires for shadow-internal form changes.

## 2. How the solution works

The POC ports the prior `SR-4788-zoning-shadow-dom-support` branch (which already solved 1–3 and
the observer half of 4) onto current `main`, then fills the remaining gaps (change events, the
hierarchy boundary marker, labeled-event matching, masking, a local opt-in). Everything is gated:
**with the feature off, every code path is behavior-identical to today.**

### 2.1 True event target — `composedPath()[0]`

`DataExtractor.resolveEventTarget(event)` returns `event.composedPath()[0]` — the unretargeted
origin — when shadow support is on, falling back to `event.target` otherwise. This is the same
idea Session Replay's rrweb uses (`getEventTarget` in rrweb-record); rrweb's copy is an unexported
bundle internal, so the SDK carries its own 5-line equivalent. For **closed** roots
`composedPath()` still yields the host, which degrades to exactly today's behavior.

Used by the click pipeline, the change pipeline, the cursor-pointer check, and action-click
resolution (`track-action-click.ts`).

### 2.2 Boundary-crossing ancestor walks

The single primitive is `composedParent(el)` (in `@amplitude/element-selector`):
`el.parentElement`, or — at the top of a shadow tree — `el.getRootNode().host`.

- `getClosestElement(el, selectors, crossShadow, maxShadowDepth)` — allowlist matching walks
  into the host tree, bounded by a crossing budget.
- `getAncestors(el, crossShadow, maxShadowDepth)` — Element Hierarchy now spans
  `button → … → shadow host → … → body`.
- `closestCrossShadow(el, selector, maxCrossings)` (new) — a single-selector `closest` that hops
  boundaries; used by labeled-event matching and text masking.

### 2.3 Shadow-piercing selectors and the hierarchy marker

A flat CSS string cannot address a shadow-internal element, so the selector engine emits one
segment **per shadow tree**, joined with a delimiter:

```
div#open-host >>> button#open-btn
div#nested-host >>> div#inner-host >>> button#nested-inner-btn
```

- `segmentWalk` splits the outward walk into per-tree segments (budgeted by `maxShadowDomDepth`,
  hard-capped at 10; deeper targets get a best-effort selector for the deepest in-budget host).
- Each segment is generated by the existing engine (strategy chain **or** legacy `cssPath` —
  both wrapped by the same `withShadow` gate), scoped to its own tree for uniqueness checks.
- Positional chains inside a shadow root are prefixed `:scope > ` so re-resolution descends by
  direct child (a `ShadowRoot` has no root *element* to anchor `nth-of-type` chains against).
- `resolveSelector(document, selector)` (exported from `@amplitude/element-selector`) is the
  symmetric inverse: split on ` >>> `, `querySelector` each segment, descend through
  `host.shadowRoot` at each boundary. **Visual labeling and any consumer that re-resolves Element
  Path must use it instead of `document.querySelector`.** Closed roots return `null` gracefully.

Element Hierarchy gets one additive, optional field: a node that is a top-level child of a shadow
root carries `"shadow": true` (and its sibling indexes are computed against the `ShadowRoot`'s
children). That is the boundary marker — when a consumer walks the hierarchy downward and hits a
`shadow: true` node, the descent goes through the *previous* node's `shadowRoot`, not its
`children`. Light-DOM hierarchies are byte-identical (the field is absent).

### 2.4 Discovery: observers and change events

- **MutationObserver fan-out** (`createMutationObservable`): one observer instance is attached to
  `document.body` *and* every open shadow root — found by an initial recursive scan, plus scanning
  each mutation's `addedNodes` for late-mounting hosts (bounded by the depth budget and a
  50k-node traversal cap). This feeds exposure/zoning and viewport-content-updated.
- **Exposure seeding** uses `querySelectorAllDeep`, which unions per-root `querySelectorAll`
  results across open shadow roots.
- **Change events** (new in this POC): `change` is `composed: false` — it *never* crosses its
  shadow boundary, so no document-level listener can work. Shadow roots also can't all be known up
  front. The POC discovers them lazily from **`focusin` and `click`** — both composed, bubbling
  events that precede a user change. (`focusin` alone is not enough: WebKit deliberately does not
  focus checkbox/radio controls on click, so `change` can fire with no focus event at all — the
  click path covers that.) Each discovery event's `composedPath()` reveals the open roots on the
  way to the control; the first time a root is seen (within the depth budget) a `change` capture
  listener is attached inside it, and roots whose hosts have left the DOM are pruned on the same
  pass so SPAs don't accumulate listeners. Exactly-once emission is guaranteed by an ownership
  rule: a per-root listener only emits events whose *true origin* (`composedPath()[0]`) lives in
  its own tree, and the document listener defers **only** for origins that have a live per-root
  listener — so slotted light-DOM controls, synthetic `composed` change events (the standard
  web-component re-dispatch pattern), and changes from roots discovery never saw all emit exactly
  once. Per-root listeners re-check the gate on every event, so a mid-session disable (remote
  config) silences them immediately.
  Known gap: a change with *no* preceding user interaction after init — e.g. browser autofill
  into a never-touched shadow field — cannot be discovered in time and is missed (it is missed
  today too).

### 2.5 Configuration and gating

Two independent switches live in the shared element-selector config:

| Switch | Meaning | Default |
|---|---|---|
| `enabled` | strategy-based selector engine (existing) | `false` |
| `shadowDomEnabled` + `maxShadowDomDepth` | shadow piercing (capture + selectors + observers) | `false`, depth 1 (clamp [1, 10]) |

They can be flipped independently; `updateSelectorConfig` applies a delivery only when it
explicitly carries at least one switch, and **preserves the current value of the switch a partial
delivery omits** (so a payload flipping one can never silently reset the other mid-session).

Local opt-in for the POC/demo (no remote config needed):

```ts
autocapture: {
  elementInteractions: {
    shadowDomSupport: true,            // or { maxDepth: 3 }
  },
},
```

Remote config (`shadowDomEnabled` / `maxShadowDomDepth` on the element-selector key) can override
the local option at runtime — that is the intended production rollout path. The gate is read
lazily on every event, so a config delivery after `init()` takes effect immediately.

Everything shadow-related runs inside error boundaries (per-event enrichment, observer callbacks,
setup) — a throw degrades to an unenriched/dropped event, never a host-page crash.

## 3. Support boundaries

| Scenario | Behavior with POC on |
|---|---|
| Clicks / links / buttons in open shadow trees | ✅ captured with true element, piercing path, full hierarchy |
| `change` on inputs/selects in open shadow trees | ✅ captured (focus-driven listener discovery) |
| Nested open trees | ✅ up to `maxShadowDomDepth` crossings (≤ 10); deeper → best-effort host selector |
| Late-mounted hosts (SPA) | ✅ clicks/changes always (document listener + lazy discovery); observers via `addedNodes` scan |
| Slotted light-DOM content | ✅ tracked as light DOM (its ancestors are light DOM); no double emission |
| Action clicks (div/span with DOM change) | ✅ resolved from the true target |
| Labeled events / triggers (hierarchy CSS match) | ✅ may cross boundaries toward light-DOM ancestors |
| `data-amp-mask` on a shadow host | ✅ masks text extracted from shadow internals — mask reach is deliberately NOT bounded by `maxShadowDomDepth` (privacy must reach as far as capture) |
| Browser autofill into a never-touched shadow field | ❌ `change` missed (no discovery interaction precedes it) — same as today |
| Exposure / viewport-content-updated | ✅ pierced discovery + observer fan-out |
| **Closed shadow roots** | ❌ out of scope — events retarget to the host (today's behavior), never an error |
| `attachShadow` called on an element already in the DOM | ⚠️ clicks/changes fine; mutation/exposure observers can miss that root (no mutation record fires). Fix would require patching `Element.prototype.attachShadow` like rrweb — a global side effect deliberately avoided for now |
| Declarative shadow DOM (SSR `<template shadowrootmode>`) | ✅ open roots exist at scan time; click/change lazy paths unaffected |
| Keyboard-only flows | ✅ `focusin` fires for keyboard focus too |

## 4. What is *not* in this POC

- **Visual labeling / tagging UI adoption.** The SDK now emits piercing selectors and a marked
  hierarchy, and `resolveSelector` can re-resolve them — but the app-side tagging UI and the
  Chrome extension still resolve with `document.querySelector` and need to adopt
  `resolveSelector` (and elementFromPoint-style pickers need `shadowRoot.elementFromPoint`
  descent). SDK-side `getEventTagProps` works since it receives the element directly.
- **Query/storage semantics downstream.** `[Amplitude] Element Path` values now can contain
  ` >>> `, and hierarchy nodes can carry `shadow: true`. Backend query support (and Edward Tran's
  NOVA data-structure work) must decide how to index/match these.
- `getNearestLabel` (Element Parent Label) stays within the element's own tree.
- Frustration analytics' dead/error-click `closest('a[target="_blank"]')` checks stay light-DOM
  (frustration otherwise benefits automatically — it shares the DataExtractor seam).
- No `attachShadow` prototype patch (see table above).

## 5. Data-shape changes (only when the feature is ON)

| Property | Change |
|---|---|
| `[Amplitude] Element Path` | may contain ` >>> ` boundary delimiters and `:scope > ` segment anchors |
| `[Amplitude] Element Hierarchy` | crosses into host/light ancestors; shadow-tree-top nodes carry `shadow: true` |
| `[Amplitude] Element Tag / Text / Attributes` | reflect the true inner element instead of the host |
| Event volume | clicks/changes that were previously dropped are now emitted |

With the feature off, all outputs are byte-identical to main (locked by the 100%-coverage suite).

## 7. Demo script (5 minutes)

1. `pnpm dev` → `http://localhost:5173/autocapture/shadow-dom.html`.
2. Click **Light DOM button** — baseline event.
3. Click **open button** (inside an open shadow root) — Element Clicked arrives with
   `tag=button, text="open button"`, path `div#open-host >>> button#open-btn`, and a hierarchy that
   crosses the boundary (`shadow: true` on the shadow-tree top, then the host, section, body).
4. Type in **open input**, then click elsewhere — Element Changed arrives with the piercing path.
5. Click the **nested-inner button** — two ` >>> ` delimiters (depth 2).
6. Click the **closed** controls — retargeted to the host and dropped; no errors.
7. Click **Mount late component**, interact with it — late-mounted roots work.
8. Reload with `?shadow=off` — shadow clicks are dropped or misattributed to the bare host `div`;
   that is today's production behavior.

## 8. Known POC trade-offs (adversarial review, accepted for now)

An adversarial review of the diff confirmed and fixed several defects (composed-change fallback,
WebKit click-only discovery, mid-session disable gating, detached-root pruning, unbounded mask
reach, two vacuous tests). Three findings are accepted as documented POC trade-offs:

1. **The local `shadowDomSupport` option mutates the page-global shared selector engine** and is
   not reverted on plugin teardown — a second SDK instance on the same page inherits it. Inherent
   to the shared-singleton engine design; the production fix is per-instance engine config.
2. **Enabling via remote config after setup misses the initial exposure scan**: pre-existing
   shadow elements are only discovered for exposure from the first subsequent mutation onward
   (clicks and changes are unaffected — their gates are read per event). Fix would re-run
   discovery on config change.
3. **Off-path guarantee is per-page, not per-instance** (corollary of 1): "option absent" means
   off only if nothing else on the page enabled it.

## 9. Open questions for productionization

1. **Rollout switch**: remote config (`shadowDomEnabled`) vs. SDK option vs. both (current POC
   supports both; remote wins). Who flips athenahealth?
2. **Backend/query support** for ` >>> ` paths and the `shadow` hierarchy flag (NOVA sizing —
   Edward Tran).
3. **Visual labeling adoption** of `resolveSelector` (app tagging UI + Chrome extension).
4. **`attachShadow`-on-mounted-host observer gap**: accept, or patch the prototype like rrweb?
5. **Perf validation** on athenahealth-scale DOMs (initial scan cost, per-focusin/click path walk,
   observer fan-out) — the budget knobs exist (`maxShadowDomDepth`, 50k traversal cap) but real
   numbers are needed.
6. **Closed-shadow stance**: document as unsupported (current), or offer a best-effort host-level
   event.
7. **Per-instance selector-engine config** to remove the shared-singleton trade-offs above.
